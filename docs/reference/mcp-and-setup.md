# MCP server and host setup

Read before calling vmem over MCP, registering it in an agent host, or using the console plugin.

## MCP server

`vmem mcp` serves newline-delimited JSON-RPC 2.0 (MCP tools, protocol 2025-06-18 and earlier) on stdio. stdout carries protocol messages only; it needs no TTY and runs in agent sessions. Requests are limited to 64 KiB per frame and results to 256 KiB (a larger result becomes a structured `LIMIT` refusal); `vmem_proposal_*`, `vmem_assert` and `vmem_assertions_purge` requests have a stricter 48 KiB bound, measured on the frame as the client sent it, escapes included, before any validation, and the `vmem_assert` and `vmem_assertions_purge` replies are held to the same bound. Arguments are validated against each tool's bounded schema (`additionalProperties: false`, string/array/integer caps); invalid arguments or unknown tools return JSON-RPC `-32602`, unknown methods `-32601`, malformed frames `-32700`/`-32600`. At startup it loads every module a tool can run, the `@staix/agent-mem` root included, so a server keeps its own code and tool list when its install is replaced or a newer release is installed beside it; restart the host session to pick up the new release.

The vault set is read once at startup: every tool's `vault` property is an enum of the registered ids and defaults to the configured default vault, or the first `personal` vault (then the first vault) when no valid default is configured. Restart the host session after `vaults add/remove`. Registered spec sources are also read once when `vmem mcp` starts; restart the MCP server after `specs add` or `specs remove`. Reads go through the same index as the CLI; writes go through `applyWrite`/`appendLog` with channel `mcp`, so they require `write: mcp` and pass the same V01-V10 gates. Every tool returns a JSON result: a receipt, or `{refused: true, issues}` for policy, validation or lookup failures. Direct note-write and promotion tools (`vmem_promote`, `vmem_promote_from_amem`) return an applied-with-errors receipt (`applied: true`, `ok: false`) without `refused: true`; inspect and recover the recorded write instead of retrying it as an unapplied refusal. Spec mutations add `refused: true` only when no change was applied (`ok: false`, `changed: false`); post-publication errors return the applied receipt (`changed: true`, `ok: false`) without that marker.

Move and delete without `confirm` write nothing and return the preview and `fingerprint`; `confirm: true` requires the fingerprint recomputed on the current state, otherwise the call is refused with `V09`. `vmem_promote_from_amem` is described under [Promotion from agent-mem](promotion-and-sync.md#promotion-from-agent-mem). `vmem_promote` is described under [Org promotion and sync](promotion-and-sync.md#org-promotion-and-sync). Graph/lint tools are described under [Lint and graph analysis](analysis.md#lint-and-graph-analysis). `vmem_assert` is described under [Assertions](writes.md#assertions) and `vmem_assertions_purge` under [Purging an assertion](writes.md#purging-an-assertion); the purge follows the same two-step rule, and its preview writes nothing. Note paths in read results are relative to `notes/`.

File reads and reports: `vmem_read_file` and `vmem_list_files` read only these roots: `ops/`, `reports/`, `self/`, `templates/`, `AGENTS.md` and `README.md`. They refuse `notes/` (use `vmem_read`), `log` (use `vmem_log_tail`), absolute paths, `.` or `..` segments, dot paths such as `.git`, any symlinked component, denied paths, non-UTF-8 files and files over 2 MiB. Paging, `maxBytes` and `offset` match `vmem_read`; listings leave out dot, linked, special and denied entries. Neither tool takes a lock, touches the index or writes a file. `vmem_report` is `vmem report` over MCP: the same path rules, screening, receipt and default `EXTRACT` event (a `log` override sets another event, for example `LINT` or `GRAPH`), with `write: mcp` required; MCP events always carry the agent attribution.

The `initialize` result carries short `instructions` (under 400 bytes): the vault is durable, linked knowledge; search first with `vmem_search`, then read the best match with `vmem_read` by section; writes are validated and receipted, and because a failure after publication can leave changes behind, read the receipt and its issues before retrying. The receipt state field differs by tool: `applied` and `changes` for vault writes, `changed` for spec writes.

## Host setup

```sh
vmem setup claude            # dry-run: lists the file and change per host, writes nothing
vmem setup all --apply       # claude codex kimi pi qwen jcode
vmem setup agy --apply       # run inside the workspace; writes ./.agents/mcp_config.json
vmem setup all --undo
vmem setup all --root ~/.local/share/vmem/releases/0.3.0 --apply   # register a versioned install root
```

Setup registers one server entry named `vmem` (`<bun> --smol <package>/bin/vmem.js mcp`) by editing the host's own MCP configuration: `~/.claude.json` (`mcpServers`; `$CLAUDE_CONFIG_DIR/.claude.json` when set), `$CODEX_HOME/config.toml` (`[mcp_servers.vmem]`), `$KIMI_CODE_HOME/mcp.json`, `$PI_CODING_AGENT_DIR/mcp.json`, `$QWEN_HOME/settings.json` (all `mcpServers`), `$JCODE_HOME/mcp.json` (`servers`) and the workspace's `.agents/mcp_config.json` for Antigravity. Defaults are `~/.codex`, `~/.kimi-code`, `~/.pi/agent`, `~/.qwen` and `~/.jcode`; overrides must be absolute. It does not call host CLIs and does not need a TTY. `--root <absolute path>` registers another vault-mem install root instead of the running one, for example a versioned `<install>/releases/<version>/` that a newer release is installed beside; the root is resolved to its real path (a `current` link registers the release it names) and must hold the package's `package.json` (a plain file of at most 64 KiB) and `bin/vmem.js`. The report names the root and its version. The current registration changes only on `--apply`; running servers keep their release until the host session restarts. Run it while the host is closed: Claude Code in particular rewrites `.claude.json` while it runs and can overwrite a concurrent change.

In the host MCP configuration, apply is idempotent and touches only the `vmem` entry: other servers and settings are preserved (TOML is edited textually, so comments and other tables stay byte-identical; JSON is re-serialized with its indentation). Configuration files must be plain strict JSON or TOML; links, JSONC and unparsable files are refused per host without writing. A partial failure is reported; the command exits 1 when failures occurred and none of the requested changes succeeded. Apply records the prior `vmem` value in a receipt, `$VMEM_HOME/setup/<host>-<hash of the config path>.json`, so separate host profiles (for example two `CODEX_HOME`s) sharing one `VMEM_HOME` keep separate receipts. The receipt is written before the host file; if the host write fails, the receipt is rolled back. In TOML, every `[mcp_servers.vmem]` and `[mcp_servers.vmem.*]` table belongs to the entry, even when other tables sit between them. Undo restores that prior value (or removes the entry, and the file if setup created it and nothing else was added) only while the entry is still the one setup installed; an entry edited later is left alone and reported as `refused`. Every mode also handles the console plugin manifest (see "Console plugin"): apply writes it, undo removes it while it still points at this install.

For Claude, Codex, Kimi and Qwen, setup also installs the bundled skills into the host skill root. Undo removes only unmodified vmem-owned skills; foreign or locally modified directories are left untouched and reported. Other hosts can use `vmem skills export <dir>`; see [Skills](../../README.md#skills).

`vmem completion bash|zsh|fish` prints a completion script generated from the same command table as `--help`.

`vmem manifest --json` prints `{name, version, configVersion, mcp: {server, tools}, commands}`: the package version, the config format it writes, the MCP tools and the CLI command names from the same table, for tools that would otherwise hard-code them. A read-only tool (its `readOnlyHint` annotation) is listed as `{name, readOnly: true}`, every other tool as its plain name.

Setup also installs the 14 packaged skills into `skills/` under the Claude, Codex, Kimi and Qwen configuration roots. Pi, jcode and agy report that no skill root is configured; `vmem skills export <dir>` prepares self-contained skill directories for those hosts. Each installed directory includes the shared adapter and a `.vmem-skill.json` ownership marker. A vmem-owned tree is replaced or removed only if its files still match the recorded digest and there are no unexpected empty directories; modified or foreign trees are reported and kept. Exports refuse a destination with unrelated entries. Directory replacement uses the platform atomic rename/exchange primitive and refuses filesystems that cannot provide it.

## Enrichment intake

Enable enrichment per vault in Settings or with `vmem settings`. The MCP tools `vmem_enrichment_work`, `vmem_enrichment_intake`, `vmem_enrichment_get`, `vmem_enrichment_reconcile` and `vmem_similar` provide the offline intake and reads. Work and stored results bind to note content hashes. Input carries an unverified skill, version, model and canonical creation timestamp; stale results are refused. Embeddings use one model and dimension per vault and are rounded to Float32. They are stored with summaries and community labels under the vmem home, outside vault sync; the 128 MiB, 50,000-record sidecar fits 10,000 1,536-dimensional vectors with bounded metadata when other records leave sufficient space. Inferred links are proposed for confirmation; the `inferred_links` frontmatter list is an unverified declaration; L19 warns when a listed target has no visible body link. Facts use the assertion journal and its evidence and receipt contract. Intake reports partial success if journal or proposal publication succeeds but sidecar tracking fails; inspect the receipt before retrying. Work items marked `needs-reconciliation` must not be retried automatically. An uncertain intake leaves a durable reservation: inspect the journal or proposals, then preview and confirm `vmem_enrichment_reconcile` with `published` if it was published or `not_published` if it was not. A wrong decision can cause a duplicate or suppress work. Lint reports missing or stale vectors only when enabled. `vmem_search` accepts `model` and `vector` together for hybrid ranking; without stored vectors lexical ordering and scores are unchanged, with currently denied paths excluded. No model or embedding endpoint is called. The skill integration follow-up is [vault-mem#281](https://github.com/STAIxBWLB/vault-mem/issues/281).

## Console plugin

The Settings panel reads the selected vault and home settings. Its action previews changes to the default vault, write mode, PII patterns and graph resolution before fingerprint-bound confirmation. `vmem settings <vault> --set JSON` uses the same path; add `--confirm --fingerprint SHA` from the preview to apply. Restart the console and MCP server after changing the default vault or write mode.

`vmem setup <target> --apply` also writes `$AGENTHUB_HOME/console/plugins/vmem.json` (default `~/.agenthub`; directory 0700, file 0600) with the absolute path and sha256 of `src/ui/plugin.ts`. `acon ui` then shows a Vault area. The panel needs agent-console 0.1.0 or later, the first release with the `host.ui` panel kit and `ui.button`. An older acon still loads the plugin, but the panel then fails with a TypeError on `host.ui`; upgrade agent-console to fix it. Re-run setup after upgrading vmem: acon refuses a module whose hash changed.

- Panels: Overview (vaults, maps, recent log), Search, Note (body, links, actions), Promote (agent-mem candidates), Lint (typed findings linked to notes), Log (parsed rows), Proposals, Assertions, History and Graph.
- Inbox: promotion candidates (group `candidate`), lint errors, a stale graph report and org-vault sync pending (group `alert`). Sync pending counts uncommitted paths plus local commits ahead of the upstream tracking ref; without an upstream it counts only uncommitted paths. It reads local Git state only (no fetch or credential prompt) and opens Overview with that vault, with no one-key sync verb. The palette searches notes.
- Inbox snapshots share one background refresh, with one worker source at a time. A cold snapshot waits at most 700 ms and then shows a refreshing status row; `refreshing: true` also marks an active collection. Later snapshots keep serving the last complete rows while refreshing. A source failure retains its last rows; if every source is unavailable at startup, a separate unavailable status row opens Overview and advises checking System. Snapshots are cached by the registered vault logs and registry metadata (inode, size and nanosecond modification/change times), a 256-byte log tail and the size-limited registry contents, without opening Git or scanning notes on a warm poll. Applied console writes invalidate freshness even if their log receipt failed. Revision-triggered refreshes wait at least 10 seconds from the start of the last collection, so sustained vault log appends cannot rerun every source on each poll, while an applied console write still refreshes on the next poll. A matching numeric `after` cursor returns only `{changed:false,cursor}`. An in-flight first collection waits only on its first request, so repeated rail polls return immediately. A 60-second safety refresh retains freshness for new agent-mem candidates, direct edits without a log receipt, and failed-source retries.
- Promote scans are single-flight and cached by the same revision, with the same 60-second safety refresh. Brief candidate titles are capped at 160 characters; pages include at most 32 KiB of serialized UTF-8 JSON, including their envelope. `nextPage` is passed back as `page`; an actually changed candidate set makes a stale page restart at the first page, or the selected candidate, and the panel hides `First page` when that reply is page 0. Identical rescans keep page tokens and conditional cursors stable. Unreadable revision evidence degrades to a stable error stamp; source collection retains its existing failure isolation and recovers when the file is readable again. A matching `after` cursor returns `{changed:false,cursor}` for that page and selection. Failed scans reuse one error cursor until a scan succeeds, so the panel does not rebuild the same error view on each poll; recovery sends full rows even if candidates are identical. Under continuous revision changes, collection makes at most two scans per request and serves the last completed pages at their old revision; the next request retries freshness. The manifest declares snapshot reuse for agent-console 0.2.0 and later: `maxAgeMs` 7500 on Overview, Promote, Lint, Log and Graph, and `inboxMaxAgeMs` 7500, half the 15-second poll. The shell reuses a reply for that long, may serve it stale once more while it refreshes, and drops it on every console action, so the shell cache never holds a reply past the next poll. That bounds only the shell's reuse: a change made outside the console still reaches a panel through the provider caches above, so a logged CLI or MCP write shows by the next poll, while a new agent-mem candidate, a direct edit without a log receipt or a lint result can wait for the 60-second refresh. Note and Search answer the person's own input and keep the shell's 2-second default. An older acon ignores the hints.
- The inbox returns at most 50 rows, errors and alerts first, then newest candidates, with titles capped at 160 Unicode code points and detail at 240. `more` counts omitted rows. Because agent-mem limits candidates per project and exposes no total-count API, vmem fetches 51 per project to detect overflow: when `moreIsLowerBound: true`, read `more` as "at least N more", not an exact total. That lower bound does not decrease when candidates are added to the same population, but may stay flat once a project reaches the fetch limit. A source failure retains its previous count too. Full candidate and lint details are available in their panels. Each source has a 30-second budget to initiate worker termination; shutdown may wait for an active native call, without blocking inbox responses.
- Actions: `delete`, `move`, `promote` (to an org vault), `promote-from-amem`, `proposal-apply`, `proposal-reject` and `link` reuse the two-step MCP tools. `link` (`from`, `to`, `relation`, optional `context` and `bidirectional`) uses the opt-in two-step mode of `vmem_link`; its preview names both notes, the relation and the log event, and an existing link is a successful no-op. Each first answers a preview with the planned changes; the write happens only after the console's confirm dialog, and only while the fingerprint still matches.
- The provider calls the `vmem mcp` handlers in process, so the console has exactly the MCP rights: writes need a vault with `write: mcp`, and log lines carry the agent attribution.
- Proposals, Assertions and History panels reuse the existing providers through the same MCP handlers, with no second code path. Proposals lists `vmem_proposal_list` pages (param `state`, default `pending`; the page cursor travels as `page` because the console owns `after`) and shows one proposal with `id` through `vmem_proposal_show`. The `proposal-apply` and `proposal-reject` actions keep the MCP two-step contract: a preview with its fingerprint first, the write only after the confirm dialog and only on the same fingerprint. Rejection needs a `reason` and changes no note or log. Assertions answers `vmem_assertions` with its parameters (`subject`, `relation`, `at`, `asOf`, `history`, `cursor`). History answers `vmem_history` for `path` and, given both `from` and `to` full commit ids, `vmem_changes` between them (`changesCursor` pages it). A refusal (unknown vault, invalid parameters, a missing or decided proposal, an unavailable commit) arrives as `error` text naming the cause and the next step; the snapshot shapes are exported as the `ProposalsSnapshot`, `AssertionsSnapshot` and `HistorySnapshot` types. These panels add no MCP tool or argument, so no vault skill follow-up is needed. An acon without them still shows the earlier panels, and the kit-based `panel.js` needs no UI package. N-1: 0.10.x and 0.11.x run beside this line on the same vaults and home. The index format, CLI commands and MCP tools are unchanged by this change and it adds no configuration keys (config format 5 comes from the settings change), so each surface is shared as is; CLI output matches 0.11.x apart from the `settings` command, which the settings change added and neither 0.10.x nor 0.11.x has; 0.10.x status and doctor also do not report the agent-mem version and host API. This change itself adds no CLI command. Only this console provider differs.
- History pages through `continuation` as `cursor` (Older revisions), changes through `changesCursor` (More changes). Assertions adds `warnings`: every coverage gap the reader reports (untrusted, unsupported, torn tail, partial batch, purged, uncommitted assertion files, index issue) with the available excluded-entry counts and its next step; `assertionCoverageWarnings` builds them and is exported with the `CoverageWarning` type.
- Graph returns schema-1 columnar pages with note and unresolved-link placeholder nodes followed by indexed edges. Snapshot edges include directed `supersedes` and `superseded_by` frontmatter references, with the source note and field preserved; the existing CLI and MCP graph outputs are unchanged. `next` travels as `page`; invalid, stale or cross-vault tokens ask to restart. Each JSON reply stays within 1 MiB, including the numeric conditional `cursor`; a matching `after` returns `{changed:false,cursor}`. Assemblies share a single in-flight build per vault, use the existing revision stamp with a 60-second refresh, and retain at most two vaults by least recent use. `neighbors` (with `hops`, `limit`, `relation`) and `from`/`to` (with `maxHops`, `viaHubs`, `relation`) call the existing graph MCP handlers. `GraphSnapshotPage`, `GraphPanelPage`, `GraphNodeColumns` and `GraphEdgeColumns` are exported from `./ui-plugin`. The Graph snapshot adds no MCP graph tool or argument.
- When enrichment is enabled, the first Graph page adds `enrichment` with the current model (null until the first vector), current-embedding count and snapshot-note total. `similar` and optional `limit` use the `vmem_similar` checks and return its hits. `semantic: {k, minScore}` (k 1..20; score 0..1) returns exact top-k undirected, deduplicated cosine edges in `semantic` columns indexed to the Graph nodes. Pass the same semantic parameters and `next` as `page` to continue; tokens bind the graph revision and parameters. A denied note causes the whole graph snapshot to be refused under the shared analysis policy; stale notes supply no vectors, and vectors never appear in replies. Up to four semantic query results per vault are cached within the existing two-vault, 60-second revision cache. Sidecar replacement changes the revision. Semantic requests with more than 3,000 current embeddings are refused before similarity computation; `similar` and the capability remain available. Exact construction costs O(n² × dimensions): on a local synthetic sample, 10,000 two-dimensional vectors at k=10 took 1.15 s; a 200-note, 1,536-dimensional sample took 31.5 ms, which extrapolates to approximately 7.1 s at 3,000 and 79 s at 10,000 notes. These are estimates, not end-to-end measurements; 10,000 exceeds the supported semantic bound. Actual time depends on dimensions, data and hardware.
- The module is exported as `@staix/vault-mem/ui-plugin`. Lint results are cached for 60 seconds per vault.

`vmem_assertions` is a read-only temporal journal query. Its `asOf`, `at`, `history`, `limit` and `cursor` parameters follow the assertion read contract in [reads](reads.md#temporal-assertions); it rechecks current policy and returns a bounded JSON-RPC response.
