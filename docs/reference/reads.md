# Reads

Read before relying on search ranking, link resolution, paging, the derived index cache, `brief`, `stats`, Git snapshot history or the frontmatter library.

## Indexed reads

```sh
bun bin/vmem.js rebuild personal
bun bin/vmem.js search personal "project discovery" --type insight --domain research --limit 20
bun bin/vmem.js show personal "Note or alias" --max-bytes 16384
bun bin/vmem.js links personal "Note or alias" --limit 50 --json
```

`--type` and `--domain` keep only notes whose frontmatter `type` and `domain` equal the given value. Validated writes accept these note types: <!-- facts:note-types -->`insight`, `decision`, `observation`, `person`, `project`, `method`, `moc`, `reference`<!-- /facts:note-types -->.

All four commands require a registered vault id. They read only flat, regular `notes/*.md` files (case-sensitive `.md` extension), skip subdirectories and symlink files, and refuse a replaced vault/notes directory. Notes are limited to 2 MiB each. They never write note content, registry configuration or `.obsidian/`. `rebuild` rebuilds the derived cache; other commands scan metadata on every invocation and rehash new or metadata-changed files. Content-identical changes only update metadata; deleted/renamed paths leave the index. SQLite transactions make each scan atomic. A concurrently changing note aborts that scan, so retry after its writer finishes. No watcher, model calls or embeddings run.

The cache is `$VMEM_HOME/indexes/<canonical-vault-path-sha256>-links<N>-schema<S>.sqlite` using the resolved home, not necessarily the environment variable. `N` is the link-resolution version (currently <!-- facts:index-links -->2<!-- /facts:index-links -->) and `S` the index schema version (currently <!-- facts:index-schema -->4<!-- /facts:index-schema -->; schema 2 added the CJK bigram table, schema 3 the reference identifiers and schema 4 the arXiv id reference notes are searchable by), so two installed vmem versions that resolve links or store the index differently keep separate caches instead of rebuilding each other's; 0.2.4 and older use the unversioned `<sha256>.sqlite`, 0.3.0 through 0.3.3 use `<sha256>-links2.sqlite`, 0.4.0 uses `<sha256>-links2-schema2.sqlite`, 0.5.0 through 0.5.1 use `<sha256>-links2-schema3.sqlite`, 0.6.0 and later use `<sha256>-links2-schema4.sqlite`, and a first run after upgrading builds the new file once with no manual step. Cache files use mode 0600 on creation. The location must be outside every registered vault, including through symlinks; linked cache directories/files are refused. It contains note text and is disposable private derived state. Removing it while commands are stopped allows the next read to build it again. SQLite uses its own transaction lock and a five-second busy timeout. There is no automatic migration or live vault cutover.

Search uses FTS5 `unicode61` over title, description and body with BM25 weights 5:2:1, ascending score and path tie-breaking. Whitespace-separated query terms are literal AND terms, not a raw FTS expression; quote the query as one shell argument. A term whose letters and digits form one run of 2 or more Hangul, Han, Hiragana or Katakana characters (surrounding punctuation is ignored) matches wherever it occurs in the title, description or body, including particle and compound forms: `사업단` finds `사업단은`, `사업단장` and `해외사업단`. That matching uses a side FTS5 table of overlapping character bigrams (Unicode NFC), so a 2-character term is one indexed lookup and a longer term a phrase of consecutive bigrams; it is substring matching, not morphological analysis. Every other term, including Latin words, single CJK characters and terms mixing CJK with Latin letters or digits (`AI교육`), keeps `unicode61` token matching, and a query without CJK terms ranks exactly as before. With a CJK term, notes where every CJK term is a standalone word or occurs in the title or description rank before notes that contain it only inside a longer body word; within each group BM25 over the bigram table (5:2:1) and path break ties, and the snippet is a body window around the first CJK term. `--type` and `--domain` are exact scalar frontmatter filters. Results include a bounded snippet and metadata, not the full body. Search queries and note targets accept at most 1024 UTF-8 bytes. Search/links default to 50 results, with an enforced 1..500 range. Show defaults to 16384 UTF-8 bytes and permits 1..65536, returning `truncated` and the full note SHA-256. `--section "Exact H2"` selects one real H2 through the next H1/H2, including its H3 children; code-fenced headings are ignored and duplicate/missing names refuse. Truncated reads include bounded `headings` (at most 64 names/8KiB metadata; `headingsTruncated` when omitted) and `nextOffset`. `--offset N` is a UTF-8 byte offset within the selected section or whole note; use the returned `nextOffset` to page even a single section larger than 64 KiB, and compare note hashes across pages. Invalid UTF-8 boundaries and zero-progress byte budgets refuse. Link string fields are capped at 1024 bytes in command results. Oversized arguments fail instead of silently raising a bound.

Link resolution uses NFC and case-insensitive filename stems only, as Obsidian and `vmem lint` L01 do. Frontmatter `aliases` (string or string array; legacy `alias` accepted) are not link targets; `show`, `links <target>` and `vmem_read` still find a note by alias. A link that only an alias matches is a missing-note link, so the writer refuses a new one and org promotion drops it to text. An optional `notes/` prefix and `.md` suffix are accepted. `[[target|label]]`, `[[target#heading]]`, `[[target#^block]]`, `![[target]]` and same-note anchors work. ATX/Setext headings and end-of-line block ids are checked; fenced code is skipped. Missing/ambiguous targets and missing anchors remain explicit with a reason. Stems that differ only by case or Unicode normalization are ambiguous. Reported `path` values are the on-disk file names byte for byte, while targets (`show`, `links`, `vmem_read`, wiki-links) are compared after NFC: a note another tool saved under an NFD name is found from an NFC target and reported under its NFD name. Links returns outgoing links in source order, with one-based body-relative `line` values (frontmatter excluded); it does not write backlinks or repair dead links. A dead link is also offered at most one suggested existing target: the closest indexed title to its text, with its positive title score, above a minimum score. `links` returns it as `suggested` on the dead entry, and `vmem lint` L01 names the same one. A text that mixes Hangul and Latin is ranked and thresholded on both parts added together, so a Hangul phrase most titles share cannot hide the one title that carries the whole text. A hint is looked up for at most 1024 UTF-8 bytes of the raw link text, the bound a reported link target is capped at, and the bound is read on the raw text before a control character is read as the separator the index already tokenizes it as, never on the capped target a row displays, so `links`, `vmem_links` and `vmem lint` name the same hint for the same dead link and a longer text gets no suggestion. A text FTS cannot parse is a miss rather than an error. It is a hint only; nothing rewrites the link.

`parseFrontmatter` retains source bytes alongside semantic YAML data using Bun's built-in YAML parser. `emitFrontmatter(document, changes)` returns the entire note, preserving omitted and semantically unchanged keys byte-identically (comments, quoting, sequences, one-level mappings, folded/literal/chomped scalars, BOM and line endings). Changed keys use canonical JSON-compatible YAML; `undefined` removes a key. Editing requires a block mapping, while an unchanged flow mapping round-trips. This is a library transformation only, not a note-write command. Synthetic fixtures and create/edit/delete/rename parity tests cover this increment; Linux/macOS CI remains the platform verification gate.

## Intent-scoped brief

`vmem brief <vault> --for "task intent" [--paths src/file.ts]... [--bytes 256..4096] [--json]` returns screened note pointers, without bodies. `vmem_brief` takes `intent`, optional `vault`, `paths` (array) and `bytes`. Use `vmem_read` for a selected note. This command does not inject anything into SessionStart or another host.

MCP `vmem_search` also accepts an optional caller-supplied vector and model for hybrid ranking when matching stored vectors exist. Without stored vectors it keeps lexical ranking; `vmem_similar` finds related notes from stored vectors. Vectors come from opt-in enrichment, not model calls by vmem.

Intent words and path basenames are literal OR terms, ranked by the existing FTS5/BM25 weights and CJK substring rules. The first five safe hits seed incoming/outgoing one-hop neighbors, marked `[neighbor]`; remaining direct matches follow. Each line names the literal note path, title, type and description. PII warnings/errors under the vault's notes-surface policy and secret-looking metadata omit the whole pointer, including neighbors. Each title, type and description is screened independently (including anchored patterns), in addition to joined metadata and the final output line. Denied files are excluded before metadata refresh reads them. Already-indexed denied rows and their link resolution are preserved for other readers; new denied files stay unindexed, and brief output filtering suppresses every denied pointer before metadata lookup or budget consumption. Restricted rebuilds are refused before clearing the shared search tables; use a restricted metadata refresh or an unrestricted rebuild. Existing metadata refresh may update only the derived cache; no vault note, log or configuration is written.

The default cap is 1024 UTF-8 bytes, range 256..4096. Both the serialized result JSON (`vault`, `lines`, `omitted`, `bytes`) and plain text including its omission footer fit the cap; `bytes` is the serialized JSON size. Lines are never truncated: `omitted` counts unique matching/neighbor paths not emitted because of policy, metadata/read limits or the output cap. Input is limited to a 1024-byte intent and 16 path hints of 1024 bytes each, producing at most 32 search words / 4096 bytes. Ranking/neighbor sets each refuse above 10000 paths; metadata attempts cap at 512 and 256 KiB per call, with each row limited to 4096 bytes inside SQL before decoding. Oversized metadata is omitted whole. The index supplies path/metadata only for selection, never body snippets.

## Evidence verification

`vmem evidence <vault> <note> [--json]` and `vmem_evidence` (`path`, optional `vault`) check a note's optional `evidence` frontmatter: a list of 1..16 entries (at most 16 KiB serialized), each `{source, sha256, quote, section?}`. `source` is one existing source reference that is also listed in the note's `source`, `sha256` is 64 lowercase hex characters of the full source file, `quote` is 1..2048 UTF-8 bytes and `section` is one exact H2 heading of at most 1024 bytes. Evidence says that quoted bytes occur in one version of a source. It does not say that a claim is true and carries no probability.

Only flat `notes/*.md` files of the same registered vault are verified. The path is resolved against the workspace root of the vault's project `registry` (as for `source` paths), followed through symlinks and must land in that vault's `notes/` directly; an unresolved path is never reinterpreted as vault-relative. Without a registry the entry is `unsupported` with reason `unresolved_source_root`; the process working directory is never used. The registry is reloaded on every call. URL and `mem:` references are `unverified_external` without any I/O or network access.

The result is `{schemaVersion: 1, vault, note: {path, sha256}, evidence: [...], truncated: false}`. Each entry has `index`, `source`, `kind`, optional `section`, `expectedSha256`, `observedSha256` when the source was read, `status`, optional `reason`, `matches` and, for a single match, `match: {start, end}` as zero-based UTF-8 byte offsets in the full source file. Statuses: `verified` (hash equal, one match); `stale` (hash differs, reason `sha_mismatch`); `missing` (`source_not_found`, `section_not_found` or `quote_not_found`); `ambiguous` (`quote_ambiguous` or `section_ambiguous`); `unverified_external`; `unsupported` (`outside_vault`, `denied`, `oversized`, `invalid_utf8`, `not_a_file`, `unresolved_source_root` or `invalid_metadata`). A missing or duplicated section never falls back to another section or the whole file. Quotes and source text are not echoed. Sources follow the note size bound (2 MiB), deny paths and the no-symlink rule. The read writes no note, log or cache and takes no lock.

New malformed `evidence` is a V01 write error under the existing baseline policy; a later change to a cited source shows up as lint L16, never as a refusal of an unrelated write. Org promotion keeps entries whose source resolves to a note of the target vault and URL entries; it removes the others and lists them in `evidenceRemoved` by index and reason only.

## Vault statistics

```sh
vmem stats personal --json             # log window: last 30 days
vmem stats personal --days 7 --json
```

`vmem stats <vault>` and `vmem_stats` report note counts (total, by `type`, `domain` and frontmatter `status`; empty values count as `(none)`), notes whose indexed mtime falls in the last 7 and 30 local calendar days (today included), and log event counts by type dated on or after `log.since`, the first local date of the `--days` window (1..3650, default 30). Known types always appear, unknown ones count as `(other)`. The derived index cache is refreshed as by every read command and the log is streamed with the bounded log reader; no vault file or log is written and no vault or log lock is taken. When the log cannot be read, `log.total` and `log.byType` are null, `log.issues` names the cause and the CLI exits 1.

`size` adds the note text size in bytes and words, as `total` and by `type` and `domain` (`{ notes, bytes, words }` each); words are the whitespace-separated tokens of the stored source, frontmatter included. `ratio` compares each note with the workspace files its frontmatter `source` cites: the note's byte size over the summed size of those files, reported as `median` and `p90` over the notes that qualified (p90 by nearest rank, both null when none did), with `overOne` counting the notes larger than their sources and `largest` listing up to five of them by ratio. `notes` and `sources` are the counts behind those figures. Each source counts at its own byte size on disk, not at the size of its decoded text, so a file that is not UTF-8 contributes its real bytes instead of the three bytes each invalid byte becomes when decoded. `skipped` counts only the source references left out of the ratio, `skippedNonFile` of them memory ids or URLs rather than files; a path is skipped too when it is denied, missing or unreadable, is past the 2 MiB auxiliary read bound or past the bytes the budget has left, or the call reaches its own limits. Those limits bound the reads and not only the counts: 64 MiB of source bytes and 10000 read attempts, failed or not, where each read asks only for the bytes the budget has left, a larger file is refused from its size without being read, and nothing further is opened once the budget is spent. A note whose readable sources total zero bytes has no ratio and is counted in `emptySourceNotes` instead, so a file that was read and found empty is never also reported as a skipped reference. `truncatedNotes` counts the notes that declare a `source` but fall past the index's 10000-note cap, in path order, so the figures describe those notes and not every sourced note. Source paths resolve from the workspace root found by walking up from the vault's registered project registry; a vault with no registered workspace reads nothing and skips every entry. A note without a `source` is not part of the ratio. The pass reuses the bounded auxiliary reader, which follows no link, and writes neither the vault nor the sources.

`vmem_list` pages the whole vault: pass the returned `nextCursor` as `cursor` to get the next page in path order. The cursor is the previous page's last path (exclusive), so a note added or removed between pages does not repeat or skip the others; a cursor outside the `prefix` filter is refused.

## Git snapshot history

```sh
vmem history personal "Note or alias" [--limit 1..100] [--cursor C] [--json]
vmem show personal "Note or alias" --revision "<full commit id>" [--section "Exact H2"] [--offset N] [--max-bytes N] [--json]
vmem changes personal --from "<full commit id>" --to "<full commit id>" [--limit 1..500] [--cursor C] [--json]
```

The JSON shapes are `history` `{schemaVersion, basis, vault, head, firstParent, renamePolicy, timeBasis, coverage, dirtyNotes, dirtyNotesReason?, capability?, path, revisions: [{revision, blob, bytes, committedAt}], scanned, scanLimit, pageLimit, stopReason, truncated, continuation?, skippedSymlink}`; `show --revision` `{…the same basis fields…, path, found, revision?, blob?, sha256?, bytes?, content?, truncated?, section?, offset?, nextOffset?, headings?, headingsTruncated?, transportLimited?}`; and `changes` `{…the same basis fields…, from, to, changed: [{path, status, before, after}], total, truncated, continuation?, skippedDenied, skippedSymlink}`. `before` and `after` are full blob ids, or `null` where the path was added or deleted.

`vmem history`, `vmem show --revision`, `vmem changes` and the MCP `vmem_history`, `vmem_changes` and `vmem_read` (`revision`) calls read Git commits as read-only snapshots of the same note paths the current readers serve. The vault's registered root must be the repository top level. Every result carries `schemaVersion`, `basis: "git_snapshot"`, the pinned `head`, `firstParent: true`, `renamePolicy: "exact_path"`, `timeBasis: "git_commit_metadata_not_assertion_time"`, a `coverage` object, and a separate `dirtyNotes` count of uncommitted note paths (`null` with `dirtyNotesReason` when Git status is unavailable). Git status, the index, refs and vault files are never written: no checkout, fetch, network, hook, filter, textconv or external diff runs, and the hardened argv/env drops inherited `GIT_*` overrides.

A revision argument must be one full lowercase SHA-1 or SHA-256 commit id reachable from the vault HEAD, resolved once and pinned for the request; `HEAD`, branch names, prefixes, revision expressions and option-like input are refused, as is any commit object outside HEAD's history or missing from the object database. A note path is data, never an expression: one carrying a control character, a backslash, a dot segment or over 1024 bytes is refused before any Git call, and every note path is passed to Git literally. `history` lists one exact note path, newest first, with full commit id, note blob id, byte size and the commit's own committer time. It follows first parents only, so a merge is the boundary for a note changed on a merged branch, and it does not follow renames: the old path's history ends at the rename and the new path starts there. Commit messages, authors and paths outside `notes/` are never returned. A target that is not the literal `notes/<path>.md` is resolved by stem or alias like `vmem show`; a deleted note needs its full path.

`history` traverses at most 1000 first-parent commits per request (`scanned` counts those commits, not the ones that touched the note) and returns at most 100 revisions per page under one 5 s subprocess deadline, naming `stopReason` (`page_full`, `scan_limit`, `history_end`, `transport_limit`) and, unless the history ended, an opaque `continuation` to pass back as `--cursor`. The cursor pins the HEAD the first page saw, so later commits do not shift a page; it resumes only from a commit on that pin's own first-parent chain, and a cursor from another note path, another revision pair, another provider, a commit off the chain or a commit the repository no longer holds is refused with `restart without --cursor`. A scan-limited page with no matching revision still continues, from the last commit the window traversed. `show --revision` reads one historical blob with the current reader's rules: the same paging (`--section`, `--offset`, `--max-bytes`), the same 2 MiB note bound, and refusal of non-UTF-8 blobs, symlinks, denied paths and non-regular tree entries. A path that did not exist at that revision returns `found: false` rather than the current content. `changes` compares two pinned commits over `notes/` only, reporting each path's status (`A`, `M`, `D`, `T`) with its before and after blob ids, never a content diff, and skipping denied and symlinked entries after counting them; it pages at 500 paths.

A repository can configure commands and path rewriting for itself. `log.follow`, `log.showSignature` and `gpg.program` are pinned off and empty on every call, so a signature header never starts a program; a clean filter attributed to any `notes/` path stops the `dirtyNotes` count (`null` with `dirtyNotesReason`) rather than letting `git status` run it. The hardened repository is read, never reconfigured.

Every complete CLI or MCP response stays within 48 KiB including its envelope and JSON escaping, measured on the JSON-RPC frame that carries it (so every payload byte is counted twice through its escaping), and a page is trimmed, with its continuation and a heading list cut if need be, rather than refused by the transport bound. A non-repository directory, a repository above the vault root, unavailable Git, a repository without commits, a shallow clone and a missing commit or blob are reported as explicit `capability` values (`not_a_repository`, `vault_not_repository_root`, `git_unavailable`, `no_commits`, `shallow_history`, `object_unavailable`) with `coverage.complete: false` where the history is incomplete; a historical read of a pruned or missing object answers `found: false` with that capability instead of refusing generically or serving current content. None of them falls back to current note content, and there is no `as_of` parameter, no historical full-text search and no claim that a commit time is when a note's statements became true.


## Temporal assertions

`vmem assertions <vault> [--subject S] [--relation R] [--at DATE] [--as-of INSTANT|DATE] [--history] [--limit N] [--cursor C] [--json]` and the read-only `vmem_assertions` query the verified assertion journal. `at` is the civil day to evaluate; `asOf` is the record-time cutoff. A date cutoff includes the entire UTC day, while an instant is inclusive. Without `at`, no world-time answer is inferred. History returns revisions and retractions, including `recordedAt` and `replacedAt`.

Each result names its journal `pin`, coverage and `basis: assertion_journal`. The current deny-path and content policy is applied on every request. A denied evidence entry is withheld without its path, quote or hash; a deleted source is unavailable. Subject note links report present, missing or superseded and do not change assertion identity. The latest subject entry within the as-of cutoff supplies the note, ordered by effective record time, segment and sequence; an earlier cutoff still shows the earlier note. A request returns at most 100 items and a continuation cursor; each encoded response is bounded to 48 KiB including the MCP envelope. A cursor is refused if the query or verified journal changed.

With `at`, each page includes the overlap groups touched by that page's items. Each group contains the ids on that page, `size` for the total group membership and `possible` when any member has an unknown answer. Page a subject and relation query to collect all member ids.

A purged assertion (see [writes](writes.md#purging-an-assertion)) is never placed in a `--subject` or `--relation` answer, because its subject and relation are gone from the journal; an unfiltered `--history` still lists its entries by id, segment, seq and hash with `purged: true` and `availability: "unavailable"`, and every read counts the assertions it holds back in `coverage.purged`. The purged entry keeps no value, evidence or source.

The SQLite projection lives under `VMEM_HOME/indexes/`, outside registered vaults, and is disposable. Each read verifies the journal again; the cache is never evidence of journal integrity. If the cache cannot be refreshed or opened, the read evaluates the verified journal directly and `coverage.indexIssue` names the cause and next step. Denied source entries appear as `{ "withheld": true }`. A missing journal returns empty results. The command does not modify notes, journal lines or the log, and takes no assertion append lock. The projection stores the verified entries as they are, so a purge deletes and rebuilds it under `assertions.lock`; if a read that started before the purge replaces it afterwards, the next read rebuilds it from the purged journal, and deleting `VMEM_HOME/indexes/assertions-*.sqlite` clears it.
