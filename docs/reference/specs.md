# Spec sources

Read before registering a spec repository or reading, validating, creating, updating or deleting specs.

## Spec source registry

Register a local repository as a separate spec source:

```sh
vmem specs add project-specs /absolute/repository --write none --pii deny
vmem specs list --json
vmem doctor --json
vmem specs remove project-specs
vmem specs remove project-specs --confirm
```

The config `specs` array holds `id`, canonical git working-tree root `path`, `write` (`mcp|cli|none`, default `none`) and `pii` (`allow|deny`, default `deny`). IDs are unique across vaults and spec sources. A spec source does not need a `notes/` directory. Registration and removal reuse the vault registry lock and atomic config write. Removal previews first, then `--confirm` unregisters only; repository files remain in place.

Config writes containing `specs` use at least format 2; vault `domains` requires format 3 and vault `canonTables` requires format 4. Without these fields, the existing serialization and version field are retained. `status` lists spec entries under a separate `specs` key, and `doctor` checks that every registered path is still its canonical git working-tree root. An unavailable or changed root makes doctor exit 1 with a per-source issue. Existing vault entries remain valid; `vaults list` also reports each effective domain set.

The registry, read-only MCP tools and CLI commands, spec creation, frontmatter-only update and two-step deletion are implemented. `resolveSpecWorktree` checks the registered git common directory; `discoverSpecs` discovers nested Markdown specs in memory; `SpecIndex` reuses the vault scanner and BM25 with a separate `spec-` cache prefix per canonical worktree. Call `scan()` to refresh a `SpecIndex`; its `snapshot()` uses the last completed scan and `search()` admits only shared-cache rows matching that snapshot's paths and hashes. Call `scan()` again to see documents another index instance inserted or replaced. A failed scan invalidates the instance snapshot; the next read refreshes it or propagates the original failure. `buildSpecGraph` resolves typed links by frontmatter id, and `specSlice` returns bounded subtree/ancestor/neighbor slices (depth 0..3, at most 500 nodes). Discovery uses Git's tracked/untracked non-ignored Markdown list, reports skipped symlinks/missing/nonregular paths, accepts NFC/NFD and filesystem case aliases, and keeps the first duplicate id in NFC path order with a diagnostic. Root device/inode identity and per-file physical containment remain checked while accepting these spelling aliases. Unknown type/status strings remain readable. To exclude large or vendored untracked Markdown, add it to `.gitignore`; already-tracked ignored files must also be untracked with `git rm --cached`. Discovery/indexing is bounded to 10000 Markdown inputs, 2 MiB each and 64 MiB total; graphs allow 10000 inputs and 100000 unique edges. Graph results omit raw note sources. Library validation (`validateSpecs`), introduced-error comparison (`introducedSpecErrors`), computed freshness (`specFreshness`), tracked-file ownership (`specsCoveringPath`) and registry-free CI logic (`validateSpecRepo`) are implemented. The read tools are `vmem_spec_get`, `vmem_spec_graph`, `vmem_spec_grep` and `vmem_spec_validate`. `vmem_spec_create` / `vmem spec create`, `vmem_spec_update` / `vmem spec update` and `vmem_spec_delete` / `vmem spec delete` are implemented (#97). No spec command runs git commit, branch or push.

Read commands share one bounded schema table with their MCP tools. `source` (CLI `--source`) defaults to the first registered source; `worktree` (`--worktree`) defaults to its registered root and must be an absolute root with the same Git common directory. Reads are allowed with `write: none` and do not edit repository content. Derived search caches stay outside protected sources.

```sh
vmem spec get goal --source project-specs --body --max-bytes 16384 --json
vmem spec graph goal --direction subtree --depth 3 --limit 100 --json
vmem spec grep implementation --type module --tag storage --limit 20 --offset 0 --json
vmem spec grep --covers-path src/index.ts --json
vmem spec validate --source project-specs --require-fresh --json
vmem spec validate --repo /absolute/checkout --require-fresh --json
```

`get` returns frontmatter, resolved outgoing links, backlinks, children, path, SHA-256 and computed freshness. Body reads are optional (`--body`, or body paging/section options) and use byte offsets with bounded UTF-8 pages. `graph` accepts subtree, ancestors or neighbors and an optional edge kind. `grep` searches FTS terms by default or a literal substring with `--literal`; filters are type, status, tag, parent, depends-on and covers-path. Use `--` before a positional id/query beginning with a hyphen, for example `vmem spec grep --literal -- "- [ ]"`. Results carry a continuation `nextOffset` when more matching hits exist. Snapshot path/hash filtering occurs before search limit/offset, so another scanner's cache rows cannot shorten pages. Rerun a command to refresh its snapshot. Large responses refuse with guidance or mark bounded collections as truncated.

`validate` exits 1 on validation errors; stale scopes become errors only with `--require-fresh`. `--repo` validates a checkout without consulting a home/config file or creating a registry/cache, and cannot be combined with `--source` or `--worktree`. The four read tools are listed by `vmem manifest --json` as `{name, readOnly: true}`; hosts that approve from a frozen allow-list instead of the manifest need to add their names separately.

## Spec validation and freshness library

`validateSpecs(snapshot, { requireFresh?, limit?, env?, git? })` returns full error/warning counts and count/byte-bounded `items`, source `diagnostics` and computed `freshness`. Types are `goal`, `architecture`, `module`, `submodule`, with increasing parent/child ranks and skipped levels allowed; status is optional or `draft|active|deprecated`. A deprecated spec may name one replacement; dangling, self or non-deprecated replacement links error, while missing or already-deprecated replacements warn. Metadata link values accept plain ids or wiki links with labels/headings. List link fields and `paths` require lists; malformed scalars remain visible to validation. `covers` and `tags` require lists of nonempty strings; scalar, non-string or empty items error. Empty lists are allowed. Only valid `covers` lists contribute duplicate claims.

Validation candidates are any `SPEC.md`, plus Markdown with parsed `id` or `type` frontmatter. A bare `SPEC.md` reports missing required keys. If YAML cannot be parsed, only the filename asserts candidacy; ordinary horizontal-rule/title-only READMEs are ignored. Oversized/non-UTF8 non-candidates yield skipped-path diagnostics; candidates retain blocking file errors. A truncated oversized frontmatter header is ambiguous and fails closed; it is never assumed to be a non-candidate. Discovery strips inherited Git pathspec-mode variables. Git binding/discovery subprocesses run outside the cache's IMMEDIATE transaction, while descriptor/path stamp checks remain inside.

`introducedSpecErrors(current, prospective, options)` compares complete internal error identities before applying display limits. Owners are matched across both trees by ids that are unique in both (including file moves), with stable file paths as the fallback for missing/duplicate-id repairs. Old owners are matched one-to-one, so a new spec reusing a moved spec's path cannot inherit its errors. Error identity also includes the repository namespace, code, field and target. Existing errors remain reportable but do not block an unrelated change; new dangling targets, cycles and rank errors are returned. Results contain only introduced errors and are bounded samples; internal resource-budget failures throw instead of returning an empty success. Spec create, update and delete use this API before publishing the prospective change. Delete allows only the preview-acknowledged dangling links to the removed id; that exception is applied before result limits so unrelated introduced errors cannot be hidden.

`specFreshness` checks full commit stamps against a pinned HEAD, counts scoped source commits and reports staged/unstaged/untracked changes touching native Git pathspecs. `paths` must be a nonempty relative pathspec list with no parent traversal and matching tracked files. Freshness is never authored into files. Stale scopes are report-only by default; `requireFresh` makes them errors. A spec without a stamp has no computed freshness entry. `git: false` skips native repository checks while retaining metadata shape/relative-path/full-SHA-format checks, and cannot be combined with `requireFresh`.

`specsCoveringPath` matches a tracked relative filename using Git's pathspec engine. `validateSpecRepo(repo, { requireFresh?, limit?, env? })` discovers and validates a checkout without reading or creating a registry, home or disk cache, returning `{ code, report }`; code is 1 for validation errors or required stale scopes. CLI `vmem spec validate --repo` implements this registry-free mode.

The portable schema contract is [test/fixtures/spec-graph/README.md](../../test/fixtures/spec-graph/README.md), with independent small valid/error/warning trees and expected codes. Consumers can copy the fixtures without a runtime dependency. Validation/CI reports omit raw sources; display limits are 1..500 records per collection and 128 KiB total, with errors shown before warnings, with `truncated` when records or oversized optional identifiers are omitted. Fixing errors and rerunning reveals later items.

`vmem_spec_create` / `vmem spec create <path> --id ID --type TYPE --title TEXT` share the create schema in `SPEC_COMMANDS`:

- The path is a literal filename relative to the selected worktree, ends in `.md`, is not Git-ignored, has no symlink component and does not exist. It must stay in that repository's discovery tree: nested repositories and submodule gitlink ancestors are refused; create the spec through that repository's own source instead. Missing parent directories are created only after validation; a failed write removes only directories it created that are still owned and empty. Create refuses before publication if a new Git-listed Markdown path would exceed the 10000-input discovery cap; ordinary Markdown and skipped tracked paths count too. Remove or ignore Markdown inputs (untrack tracked exclusions) before retrying. Non-empty parents are kept; expected retention after a refused create race is reported as a warning. Other owned-directory cleanup errors name the directory and the errno or ownership cause, with an access/ownership recovery step.
- Repository, ignore and gitlink checks run once at each create stage: initial read, locked validation and final publication check. Each stage streams the index once, retaining only whether a mode-160000 gitlink matches the target's own ancestors by canonical NFC/lowercase key, including missing workdirs and mixed normalization. There is no spelling-variant expansion. The scan bounds actual index output to 128 MiB, 1000000 records, 64 KiB per record and 10 seconds. Exceeding a bound refuses with the index cause and asks you to inspect, reduce or repair the index before retrying. Filesystem checks still run while creating parents.
- New file permissions are `0666 & ~umask`; new parent directory permissions are `0777 & ~umask`, matching editor-style creation. Updates retain the existing file mode. After publication, create syncs the immediate file parent, then the parent of each new directory, deepest first. A post-publication sync or cleanup failure returns `changed: true`, `ok: false` and "created with errors". Inspect the created file, its parent directories and the lock state under `VMEM_HOME`; preserve any replacement temporary file, and do not repeat the create.
- Titles supplied to create or update must contain no line separators or control characters (C0/C1, including NEL and NUL). Rejected inputs leave the file unchanged; the frontmatter emitter is unchanged.
- Required metadata is `id`, `type` and a single-line `title`. Status defaults to `draft`. Types are `goal|architecture|module|submodule`; statuses are `draft|active|deprecated`. Optional fields are `parent`, `superseded-by`, `depends-on`, `references`, `implements`, `covers`, `tags`, `paths` and `verified-against`. CLI list flags take JSON arrays. There is no body input.
- Frontmatter uses this field order: `id`, `type`, `title`, `status`, `parent`, `superseded-by`, `depends-on`, `references`, `implements`, `covers`, `tags`, `paths`, `verified-against`. The body starts with `# <title>`, then empty H2 sections: goal has `Scope`, `Decisions`, `Success and evidence`; architecture has `Boundaries`, `Decisions`; module and submodule have `Responsibility`, `Interfaces`, `Decisions`. New files use LF and no BOM.
- Creation uses the same write policy, raw and decoded metadata screens, worktree lock, introduced-error gate and actor attribution as update. Duplicate-id refusals name the new file even when it sorts before the existing spec. After setting the final mode and fsyncing the staged file, create publishes it atomically with a hard link and removes its temporary name. An intervening destination is preserved and refused with `EEXIST`. Other link failures name the cause and require checking permissions or using a filesystem with hard-link support; create never falls back to rename. Update publishes with rename. Spec create/update/delete use the same publication/cleanup helper as note writes: post-publication parent-identity and containment checks report drift with recovery guidance, while already-published changes retain `changed: true` and are not marked as MCP refusals. Lock/temp descriptors stay open until identity-checked unlink. A concurrent writer with the same user's access can still change the target or replace a parent between the last check and publication, or replace a cleanup name after its final identity check; pure TypeScript has no atomic inode-checked namespace primitive. Stop other writers, inspect the target, original parents, retained temps and VMEM_HOME lock state, and recover any applied change before another mutation.

```sh
vmem spec create design/module.md --id module-id --type module --title 'Module design' --parent root-id --tags '["new"]' --json
```

`vmem_spec_update` / `vmem spec update <id>` share the update schema in `SPEC_COMMANDS`:

- `set` (`--set JSON`) accepts scalar `title`, `type`, `status`, `parent`, `superseded-by` and `verified-against`. Types are `goal|architecture|module|submodule`; statuses are `draft|active|deprecated`.
- `unset` (`--unset JSON`) is a list of optional field names. `id` is immutable, and `id`, `type` and `title` cannot be unset. Unknown keys are refused.
- `add` / `remove` (`--add JSON`, `--remove JSON`) map `depends-on`, `references`, `implements`, `covers`, `tags` or `paths` to string lists. Entries are compared literally; existing entries are not added twice. A field cannot be unset and edited together, and a value cannot be added and removed together.
- Optional `expectedSha` (`--expected-sha`) takes the SHA-256 from `spec get` and refuses a stale read. The target is re-read under an exclusive per-canonical-worktree mutation lock under `VMEM_HOME`, outside every worktree. Registry/policy and spec-state changes during validation refuse rather than overwrite the new state. Update and delete ignore ordinary Markdown path-list churn in this drift comparison. Create compares the Markdown count and whether its target is listed, preserving the discovery-cap guard while allowing same-count unrelated renames; spec candidates and diagnostics still participate in every operation's drift check.
- `emitFrontmatter` preserves body bytes, BOM, original line endings, existing field order and unchanged field syntax. A semantic no-op writes nothing and returns `changed: false`. A changed file is staged in a same-directory temporary file and atomically renamed; the result names the path, SHA-256, actor and any refusal rule.
- The prospective tree is built in memory and checked with `introducedSpecErrors`: new errors refuse the write, while old unrelated errors do not block it. Refusals name the written path, with related paths/targets when needed.
- `write: mcp` permits CLI and MCP; `write: cli` permits CLI only; `write: none` refuses both. The shared `screenContent` rules always refuse secrets and refuse email/phone under `pii: deny`. The whole written text and decoded frontmatter are screened. Results carry `actor: agent` for MCP or the usual agent environment markers, otherwise `person`; no vault or source log is appended. Body prose is edited with normal file tools. Delete uses the preview-confirm flow described below.

```sh
vmem spec update module-id --source project-specs --set '{"title":"Reviewed module"}' --unset '["status"]' --add '{"tags":["reviewed"]}' --json
```

`vmem_spec_delete` / `vmem spec delete <id>` use a two-step acknowledgement:

- Without `confirm`, preview returns `preview: true`, the path, SHA-256, every backlink edge kind (body links included), children and a fingerprint. Arrays are sorted; the fingerprint binds the selected worktree, path, file SHA and the complete listed backlinks and children. Preview creates no cache, lock or file. The 224 KiB budget applies to preview-invariant acknowledgement fields, so a payload at the bound passes both preview and confirm. If it exceeds that budget, it refuses instead of omitting relations.
- Confirm with `confirm: true` and the fingerprint (`--confirm --fingerprint SHA` in CLI). The preview is recomputed under the canonical-worktree mutation lock. A changed file, child or backlink list makes the fingerprint stale and refuses deletion; request and inspect a fresh preview before confirming again.
- Only dangling frontmatter links to the removed id that the current preview acknowledged are permitted. Other newly introduced validation errors refuse. The caller repairs the listed links afterwards through spec update. Delete does not remove children or rewrite other specs.
- The same source write policy and actor attribution apply to preview and confirm. Confirm rechecks the shared registry guard immediately before unlink, removes only the selected file and leaves an ordinary Git deletion; it does not stage, commit, branch, push or append a log. Post-unlink sync or cleanup errors retain `changed: true`, `ok: false` and the SHA, with "deleted with errors" and no refusal marker. After an applied delete error, inspect the deleted file's parent directory and the mutation lock state under `VMEM_HOME`; the file is already gone. A blocked delete, including a path refusal before any deletion, directs the caller to request and inspect a fresh preview before confirming again, never to supply an update `expectedSha`.

```sh
vmem spec delete module-id --source project-specs --json
vmem spec delete module-id --source project-specs --confirm --fingerprint <preview-fingerprint> --json
```
