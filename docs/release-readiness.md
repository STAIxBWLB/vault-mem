## Release tags

- Create release tags only with `bun run release:tag`. First bump `package.json`, add a dated `CHANGELOG.md` entry, restamp stale documents in `docs/verified.json` (see [release workflow](release-workflow.md)), and merge that preparation through a PR. The script refuses while `bun scripts/check-docs.mjs --require-fresh` reports a stale document. Switch to clean, up-to-date `main` before running the script; it fetches origin/main and release tags, rejects an existing tag or a version at or below an existing release, and creates an annotated `v<version>` tag at HEAD.
- The default command creates only a local tag. `bun run release:tag --push` explicitly creates and pushes it, triggering release validation. Tag creation and publication require separate owner authorization; do not run either command as part of ordinary implementation work.
- Release validation requires the tag to match the package version and dated CHANGELOG entry, and its commit to be an ancestor of fetched origin/main. It waits up to 20 minutes for the latest `Check` main-push run on that exact SHA, refusing a failed, cancelled or skipped run, API error, or deadline with no successful run. If main Check is still queued at the deadline, re-run release validation after it turns green. PR CI alone is insufficient. Existing package/evidence gates and npm-production approval still apply.
- Branch protection/ruleset configuration is a separate owner operation after merging the workflow change. Require only `ci-ok`, which always runs after the full check matrix and refuses every non-success result, including unexpected skips.

## Scope and reproduction

- Run `bun install --frozen-lockfile && bun run check` on the exact candidate. Ordinary checks include package smoke, evidence shape/sample checks and synthetic parity checks, but do not require historical evidence digests to match current source and do not rerun the 5000-note benchmark. Run `bun run release:verify` explicitly before a release; tag validation requires it.
- Run `bun scripts/release-parity.ts --output <synthetic-evidence.json>` for aggregate fixture proof. Use the two explicit external reference flags to cross-check unchanged Python tools; reference SHA256s are recorded with evidence.
- Run authorized measurements serially on dgx02 through `remote_dev.py run --cgroup <worktree> -- 'bun scripts/release-performance.ts --output <synthetic-evidence.json>'`. The runner must export writable `REMOTE_DEV_CGROUP` delegation with the memory controller enabled. The harness puts only MCP into a fresh child before Bun starts and reads its `memory.peak` after MCP exits; this is the peak of memory charged to the MCP cgroup (anonymous, kernel and page cache it charged first). File pages first charged by the harness remain excluded, so it is not an upper bound of VmRSS. The 200 MB gate passes only when both `memory.peak` and the sampled VmRSS/VmHWM maximum are below the limit. `sampledPeakRss` remains recorded as a lower bound of the old RSS metric. Missing delegation or peak telemetry fails without fallback. Do not run it on the Mac or launch a duplicate slow run. The harness removes its own child cgroup and temporary synthetic vault.
- `bun run release:verify` accepts `peakSource: "cgroup-memory.peak"` without requiring monotonic VmHWM diagnostics; all gate fields and runtime/method/parity bindings remain required. For other peak sources, missing or decreasing VmHWM still refuses the evidence as a lower bound. The committed 0.5.1 report is unchanged and remains unverified under the newer peak-evidence rule; the 0.6.0 report keeps the cgroup measurement that release used, the 0.7.0 report is kept as that release's evidence, and the 0.8.0 preparation supplies the one described above.
- The reference source bytes used for the 0.6.0 parity run remain unchanged and retained; 0.7.0 reused that record because all eight recorded inputs still matched, and 0.8.0 reran the two rounds because `src/vault-graph.ts` changed, in the same recorded reference environment (Python 3.13.5, networkx 3.4.2, pyyaml 6.0.2). This preparation performs no reference-tool retirement or installed-tool change. The public corpus and reports contain synthetic data only. Private parity/write evidence must stay in the approved private project location and must not expose note bodies here.
- Native Obsidian acceptance used Obsidian on a Mac with no existing Obsidian profile. The app support folder created by that first launch was removed afterwards; no live vault, settings, templates or self notes were touched.
- Follow [the cutover checklist](cutover-checklist.md) for installation, registration, persistence readback, retirement and rollback. Publication and live cutover remain blocked while any required gate is missing.

## Gate commands

`bun run check` includes strict types, import boundaries, tests, package dry-run and a clean tarball installation with CLI/MCP reads, non-TTY mutation and stale-preview refusal. Package files are limited to runtime source/bootstrap, manifest, license, README and changelog. Tag validation additionally runs npm package dry-run and tests the exact npm tarball later used by the gated OIDC job. No release tag or publication is created by this readiness change. The tarball install resolves the pinned first-party dependency from the configured registry, so the full check requires network access.

- `bun run parity:release` checks same-snapshot frontmatter bytes, incremental notes/FTS/links against clean rebuild, and two consecutive synthetic Python-oracle lint/graph comparisons. External Python reference paths can be supplied with `--lint-reference` and `--graph-reference`; `--output` records aggregate evidence.
- `bun run release:verify` enforces committed runtime/method/external-parity evidence freshness and the declared synthetic thresholds at the explicit release gate. Ordinary tests validate evidence shape and internal sample consistency; routine source edits and version bumps do not require fresh benchmark evidence until release validation.
- `remote_dev.py run --cgroup <worktree> -- 'bun run bench:release --output <file.json>'` measures a generated 5000-note corpus in the authorized Linux container with writable `REMOTE_DEV_CGROUP` memory delegation. It records MCP search round-trip timings (including metadata refresh), cgroup `memory.peak`, sampled VmRSS/VmHWM, the rebuilt index size (`indexBytes`), raw samples and environment. Both peak values must be below 200 MB; charged cgroup memory excludes pages first charged by the harness and is not an RSS upper bound. The command exits nonzero when a synthetic threshold fails. Synthetic write timings are diagnostic and do not establish representative private-vault acceptance.
- This document, the [release workflow](release-workflow.md) and the [cutover checklist](cutover-checklist.md) distinguish verified results from outstanding private/native/integration/deployment gates. Live cutover is covered by the Status paragraph of the [README](../README.md).
